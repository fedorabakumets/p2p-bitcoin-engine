# P2P Bitcoin Engine

Обменник BTC за рубли. Клиент и трейдер работают через одного Telegram-бота на aiogram 3. Mini App не нужен.

Сейчас это этапы 0–7: пользователь, котировка, заявка, панель трейдера, виртуальное пополнение, эскроу, назначение трейдера и подтверждение оплаты. Сети биткоина нет: выплата клиенту — проводка ledger, без txid.

## Как запустить

Нужны PostgreSQL и Redis. Токена бота в репозитории нет: его выдаёт BotFather, и пока его нет, тесты и `python -m app.main --dry-run` работают без `BOT_TOKEN`.

```bash
cp .env.example .env
# позже: впишите BOT_TOKEN в .env
docker compose up --build
```

Compose поднимает PostgreSQL, Redis и приложение. Контейнер приложения сначала применяет миграции, затем запускает бота. Пока `BOT_TOKEN` пустой, процесс завершается с понятным текстом и без трассировки aiogram. Postgres и Redis при этом остаются запущенными.

Проверка здоровья: `GET /healthz` на порту 8000.

Локально, без Docker:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
export DATABASE_URL=postgresql+asyncpg://p2p:p2p@127.0.0.1:5432/p2p
export REDIS_URL=redis://127.0.0.1:6379/0
export BTC_RUB_RATE=6000000
alembic upgrade head
python -m app.main --dry-run
pytest
```

`python -m app.main --dry-run` не ходит в Telegram и не требует `BOT_TOKEN`. Он печатает котировку на 2000 ₽ по курсу из `BTC_RUB_RATE`.

Когда токен появится:

```bash
export BOT_TOKEN=...
python -m app.main
```

Бот сам по таймеру закрывает просроченный поиск и просроченное ожидание оплаты. Redis для этого не нужен: он остаётся таймером диалога и лимитом сообщений. Захват заявки делает один `UPDATE` в PostgreSQL.

## Что делает эта версия

- `/start` создаёт пользователя. Ссылка `ref_<code>` записывает `referred_by_user_id`. Самого себя пригласить нельзя. Повторный `/start` реферера не меняет.
- Меню клиента: Купить BTC, Мои заявки, Партнёрская программа, Поддержка.
- Покупка: сумма в рублях (это сумма, на которую клиент получает BTC), затем BTC-адрес (`bc1`, `1` или `3`), затем котировка. «Продолжить» сохраняет снимок и переводит заявку в `SEARCHING_EXECUTOR`. Подходящим трейдерам уходит уведомление.
- Трейдер — это пользователь со строкой в `traders`. У него дополнительные кнопки: Баланс, Принимать заявки, Активные заявки, Статистика, Вывод, Мой tier, Реквизиты СБП.
- Баланс читается из `ledger_balances`: доступно, заморожено и всего, в BTC с 8 знаками.
- Реквизиты СБП трейдер вводит сам: телефон, название банка, имя получателя. Бот банк не угадывает. Активный СБП один.
- «Принимать заявки» переключает `is_online`. Без активного СБП и без статуса `active` включить приём нельзя.
- «Вывод» создаёт заявку оператору и запись в `audit_log`. Баланс не списывается, автовыплаты нет.
- Поиск трейдера: `traders.status = active`, пользователь `active`, онлайн, один активный СБП, доступных сатоши хватает на `trader_lock_sats`, сумма заявки внутри минимума и максимума, дневной объём не превышен. Сообщение на русском: сумма, к оплате, способ СБП, «На карту: … ₽» (это рублевая наценка, для 2000/2360 это 360 ₽) и кнопка «ПРИНЯТЬ».
- Принятие — один `UPDATE` из `SEARCHING_EXECUTOR` в `EXECUTOR_ASSIGNED`. Второй трейдер получает «Заявка уже принята другим трейдером». В той же транзакции сатоши уходят на `trader_locked`, растёт дневной объём, заявка переходит в `WAITING_PAYMENT`, клиенту показываются реквизиты СБП.
- «Я оплатил» может нажать только клиент, и только из `WAITING_PAYMENT`. Повтор безопасен. После `CLIENT_MARKED_PAID` клиент заявку не отменяет.
- Отмена до этой отметки ставит `CANCELLED` и, если трейдер уже был назначен, возвращает заморозку на доступный баланс.
- «Подтвердить получение» ведёт `PAYMENT_CONFIRMED` → `RELEASING` → проводки → `COMPLETED`. `payout_wallet_tx_id` остаётся пустым: в сеть ничего не отправляется.
- «Открыть спор» ставит `DISPUTED`. Эскроу остаётся замороженным. Текст и скриншот пишутся как `dispute_evidence` (для картинки хранится только `telegram_file_id`). Скриншот оплату не подтверждает.
- Оператор закрывает спор командой `/resolve <номер> release|unlock`, не через сайт. `release` завершает заявку теми же проводками, что и подтверждение трейдера. `unlock` возвращает сатоши трейдеру и ставит заявку в `CANCELLED`: рубли люди возвращают сами, вне платформы. Оба действия пишут `audit_log` и доступны только `admin_users`.
- Если никто не принял заявку до `accept_expires_at`, `expire_search` ставит `EXPIRED`. Если клиент не отметил оплату до `pay_expires_at`, ожидание тоже истекает и заморозка снимается. Уже отмеченная оплата сама не истекает.
- Партнёрский экран считает приглашённых, сколько из них имеют хотя бы одну завершённую заявку, оборот как сумму `principal_rub` этих заявок, заработанные и доступные реферальные сатоши. Рубли по курсу заявок берутся из снимка. Строка «Оценка по текущему курсу» считается по `BTC_RUB_RATE` и помечена как оценка. Ссылка: `t.me/<username>?start=ref_<code>`.

Кнопки вызывают сервисный слой. FastAPI в этом прототипе — только `GET /healthz`.

## Как пополнить тестового трейдера

Пополнение виртуальное: в ledger пишется `ADMIN_ADJUSTMENT`, `+trader_available` и `-external_in`. Сеть не читается.

Пользователь сначала должен нажать `/start`. Затем один раз отметьте его администратором и, если нужна панель трейдера, создайте строку трейдера:

```sql
INSERT INTO admin_users (user_id, role)
SELECT id, 'operator' FROM users WHERE telegram_id = 123456;

INSERT INTO traders (user_id, status, is_online)
SELECT id, 'active', false FROM users WHERE telegram_id = 123456;
```

Пополнить этого администратора на 0,01 BTC (1 000 000 сатоши):

```bash
python -m app.admin_credit --telegram-id 123456 --sats 1000000
```

Команда откажется, если этого Telegram ID нет в `admin_users`.

Из бота, тоже только для администратора:

```text
/credit 1000000
/credit 0.01
/credit <telegram_id трейдера> 1000000
```

`0.01` здесь — биткоины. Целое число — сатоши. Чужой telegram id можно пополнить только командой бота: CLI зачисляет тому же id, который проверяет в `admin_users`.

Сайт администратора по-прежнему не делается.

## Чего эта версия не делает

- не подключает Electrum и не смотрит testnet;
- не принимает цепочечный депозит и не отправляет биткоин (`send_btc` нет, txid выплаты пустой);
- не ходит в платёжный процессор и не выбирает между процессором и трейдером;
- не открывает Mini App и админ-сайт;
- не хранит рублёвый баланс, который платформа кому-то должна.

Рублёвая наценка (`payment_rub - principal_rub`) остаётся на карте трейдера. Отдельной проводки `TRADER_REWARD` нет.

## Как устроены деньги

В ledger только биток, в сатоши. Клиент переводит всю сумму на карту трейдера. Наценка в рублях в ledger не проводится.

На релизе `trader_lock_sats` уходит с `trader_locked`:

- `client_btc_sats` — выплата клиенту через `external_out`, без сетевой транзакции;
- `platform_fee_sats` остаётся платформе на `platform_revenue`;
- `referral_sats` — доля этой комиссии, перевод `platform_revenue` → `referral_payable`, если у клиента есть `referred_by` и доля больше нуля. Одна строка `referral_rewards` на заявку.

`trader_lock_sats = client_btc_sats + platform_fee_sats`. Снимок на заявке повторно не считается.

Строки одной группы в сумме дают ноль. Баланс меняет только сервис ledger. Ключи идемпотентности не дают второму нажатию заморозить, отпустить или начислить реферальные сатоши ещё раз. Триггер не даёт доступному и замороженному балансу трейдера уйти ниже нуля.

Рубли хранятся целыми копейками. Стартовые настройки в миграции: жизнь котировки 120 секунд, окно «принять» 20 секунд, время на оплату 900 секунд, наценка 1800 б.п. (18%), комиссия платформы и доля реферала 0, пока оператор их не задаст.

Клиент вводит principal в рублях. К оплате = principal × (1 + наценка). При 2000 ₽ и 18% к оплате 2360 ₽, на карту трейдеру сверх суммы битка остаётся 360 ₽.

## Схема

Описание таблиц: [docs/schema-v1.md](docs/schema-v1.md).

Первая миграция Alembic применяет [migrations/001_initial.sql](migrations/001_initial.sql) как есть. Новых колонок этап B не добавляет.

Статусы заявки: `CREATED`, `QUOTED`, `SEARCHING_EXECUTOR`, `EXECUTOR_ASSIGNED`, `WAITING_PAYMENT`, `CLIENT_MARKED_PAID`, `PAYMENT_CONFIRMED`, `RELEASING`, `COMPLETED`, а также `CANCELLED`, `EXPIRED`, `DISPUTED`, `FAILED`. Переходы проверяет сервис заявок и пишет `order_events`. После `CLIENT_MARKED_PAID` клиент заявку не отменяет.
